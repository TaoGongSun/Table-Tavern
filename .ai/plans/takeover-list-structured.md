# takeover-list-structured：接管桌清單欄結構化

作者裁決 2026-10-27「takeover-list-structured 做」；總目標是之後的全自動 AVG／VN 模式。依據原則：重構目的＝省模型輸出、卡的固定資產留在骨架、舊桌不相容（限發佈前）。

## 現況
- 重構契約（`refactor_ai/prompt_common.rs` `INTERFACE_SHELL_COPY_RULES`）明令「全量清單整份做成一個欄位、值一律是一個字串」。北境驿站產物：`在場人物` 是 3 人 × 8 行的 YAML 字串（連 4／8 格縮排、`- 人物:` 外殼、每值前的 emoji 都在值裡），`行動選項` 是 4 行帶 6 格縮排的字串；guide 要 GM「縮排照抄」。
- GM 改一人的「行动」就得 replace 整串（`apply.rs` `list_refusal`、`context.rs` `push_list_field_reminder` 都這樣教）；鍵名字形漂移靠 `mechanism/list_keys/` 寫入時校正。
- 殼填值（`src/features/refactor/refactor-shell.ts`）把整行佔位符的多行值照原樣插入。

## 做法

### 1. 樹的形狀
清單欄＝`Mechanism.collections` 登記的欄位（下稱「集合」，規則仍是 `kind: list`）。兩種：
- **具名集合**（有身分的實體：人物、道具、地點）：JSON 物件、以名字為鍵，項目一律是物件（純量項目沒地方放 `_序`，具名集合不收純量項目）。`在場人物/林远/行动`。STATE 寫 `{"在場人物": {"林远": {"身份": "新任驿丞", …}, …}}`。名字只當鍵，項目裡不再放「名字」欄。
- **序列集合**（沒有身分、整批換的：行動選項、日誌行）：JSON 陣列，樹上是 `0..n-1` 索引分支（沿用 `json_to_node` 與 statusbar-yaml-list-flatten 的索引分支）。
- 序列集合的項目是物件（欄位為純量）或純量。項目內再套清單不做（深度上限 1）：卡若有，項目內那格照舊當文字欄〔模型判斷·未裁決〕。
- **集合描述（持久化）**：樹把物件與陣列都存成分支（`mechanism/tree.rs:76`），空的 `{}`／`[]` 無從分辨，所以形狀不從樹或模板推，改由一份描述記在 `Mechanism.collections`（點分路徑 → 描述），跟規則一起落檔：`{"keyed": true, "item": "object", "fields": {"身份": "text", "体力": "text", …}}`、`{"keyed": false, "item": "scalar", "type": "text"}`；欄位型別 text／number／bool（填殼時決定加不加引號，取代原本想做的 `value_types` 萬用路徑）。由 app 在套用重構時從驗證過的 STATE＋骨架＋規則產生，不由 AI 寫。驗證、套用、GM 狀態、前端填殼共用這一份。
- **順序**：樹是 BTreeMap，具名集合會依字碼排（周掌柜、林远、贺铮）。每個具名項目放一片 app 管的 `_序` 葉子（整數）：新增時取最大值＋1（同一批多筆依序遞增）、整份 replace 依 JSON 物件順序（serde_json preserve_order 是本地行為，GM 依「目前狀態」順序寫回即可保序）重編、改名（move）跟著項目走、insert 經字形折疊命中既有項目時保留原 `_序`。輸入值裡帶的 `_序`（或任何底線鍵）一律丟掉，由 app 保留或重建——底線鍵唯讀原本只查 path／from（`apply.rs:345`），整項 replace 會夾帶。殼、GM 的「目前狀態」、狀態欄三處都照 `_序` 排；`_序` 本身三處都不顯示（狀態欄 `StateBar.tsx` 只藏 `_序`，其他底線鍵照顯示——MVU 卡的底線變數玩家可能要看）。〔A 已審：Sol、Grok 同意〕
- 序列集合 remove 照 RFC 6902 往前補位（重編 0..n-1），insert `-` 接在尾端、insert `/i` 插入並後移；最後一項刪掉時集合保留為空分支（現行 `set_tree_value` 會連父分支一起剪掉）；描述在，就算樹上整支不見也照空集合看待。

### 2. 骨架：區段語法
項目格式（`- 人物:` 外殼、鍵名、縮排、引號、值前的 emoji）全是固定資產，寫進骨架，不進樹。採 Mustache 區段：
```
  人物列表:
{{#在場人物}}
    - 人物:
        名字: "👤 {{@key}}"
        身份: "🪪 {{身份}}"
        行动: "📝 {{行动}}"
{{/在場人物}}
  行动选项:
    名字: "👤 林远"
    选项:
{{#行動選項}}
      - "{{@n}}. {{.}}"
{{/行動選項}}
```
- 區段內：`{{欄位}}` 是相對項目的路徑；`{{.}}` 是純量項目本身；`{{@key}}` 是具名項目的鍵；`{{@n}}` 是從 1 起的序號。區段外的佔位符語意不變。區段與 `{{.}}` 取自 Mustache；物件逐鍵迭代與 `@key`／`@n` 是本案自訂擴充。
- 序號由骨架給：序列項目的值不含序號（契約與 GUIDE 都寫明），否則會渲染成「1. 1. …」。
- 填值是一次替換：展開區段時只複製模板、把區段內佔位符**改綁成絕對路徑**（`{{身份}}`→`{{在場人物.林远.身份}}`；`@key`、`@n` 綁成填值器認得的虛擬路徑），值一個都不先放；之後整份交給現有填值器做唯一一次替換與跳脫（引號、區塊純量規則全照舊）。值裡的 `{{…}}`、引號、換行因此不會被二次解讀，殼看到的與原卡逐位元相同。依項目順序展開（具名看 `_序`，序列看索引數值）。區段標記在 YAML 區要獨佔一行（標記行本身丟掉）；非 YAML 區（`<Item>…</Item>` 這類）可以寫在行內。
- 空集合：區段展開為零項時，若上一行是值為空的 YAML 鍵就補 ` []`，卡讀到空陣列而不是 null。
- `{{#`／`{{/` 與酒館巨集清單（`st-macros.json`，帶參名只有 `//`）不衝突。

### 3. GM 怎麼報
- 改欄位：`replace /在場人物/林远/行动`（只報變的那格）。
- 進場：`insert /在場人物/商队领头人` ＋整個物件（全部欄位）；離場：`remove /在場人物/贺铮`；改名：`move from /在場人物/神秘人 path /在場人物/沈砚`。
- 序列集合：GUIDE 與協定只教整批 `replace /行動選項` ＋ JSON 陣列（樹上索引從 0、殼上序號從 1，教逐筆 remove 會刪錯）。套用端照樣接受 `insert /-`、`remove /i`（RFC 6902 補位），只是不教。
- 用語：這是本 app 的自訂協定（`insert` 是本案命名，非 RFC 6902 的 `add`），文件與提示不宣稱照某標準。
- 系統提示：`push_list_field_reminder`（「寫出整個欄位的完整字串」）改寫成上面這份協定，只在有集合規則的桌出現；`table_update_example` 加一筆項目路徑範例（取第一條 `集合.*.欄位` 萬用規則，`*` 換成樹上第一個項目的鍵）。新文字放新檔 `transport/list_protocol.rs`，`context.rs`（989 行）只留呼叫。凍結快照會變的只有帶集合規則的桌（都是本案之後重構的新桌）。
- 「目前狀態」：接管桌是增量桌，`render_state_tree` 把分支印成巢狀「鍵：」，GM 直接看到 `在場人物：／林远：／行动：…`。本案改三處（`state_view.rs`）：集合項目照 `_序`／索引數值排，不照 BTreeMap 字碼序（否則 GM 照狀態整份 replace 會把順序蓋掉）；`_序` 不印；描述登記的集合沒有項目時照印 `在場人物：（目前沒有項目）`（巢狀集合、集合本身或祖先分支被剪掉也照印，祖先印標頭）——現行沒有可見子葉的分支標頭會被刪掉（`state_view.rs:189`），清空後集合會從提示消失。協定段附「目前沒有項目時怎麼新增」的範例（`insert /在場人物/名字` ＋物件）。

### 4. 本地套用（新檔 `mechanism/collection.rs`，`apply.rs` 只加一處掛勾）
patch 的 path 或 from 碰到集合本身、項目、項目欄位，或集合的祖先分支時先交給它：
- 值的形狀把關：具名集合整份 replace 要物件、序列要陣列；項目要物件（物件模板）或純量（純量模板）；GM 照舊寫成整串 YAML 字串的一律拒收並回饋正確寫法（自癒，不猜著解析）。
- 項目鍵（名字）只差字形時對回現有項目：`insert /在場人物/林遠` 視同改林远，不長出第二份（現行 insert 末段是新鍵、不折疊）。路徑中段的字形由既有 `canonical_path` 處理。
- 項目內欄位鍵：新增或整份 replace 帶進來的物件，鍵依 `集合.*.欄位` 萬用規則的欄位名折疊（取代 list_keys 的工作）；對不到任何欄位的鍵丟掉並回饋。缺欄位的新項目照收，回饋列出缺的欄位請下回合補。
- 寫入邊界：寫到描述沒有的項目欄位（`replace /在場人物/林远/未知`）拒收；整份替換或刪除集合的祖先分支拒收（會繞過形狀檢查）；move 只准同一具名集合內改名（目的地已有同名項目拒收），跨集合、從集合外搬進、從集合搬出都拒收；move 一律先驗證再動樹，失敗不刪來源。
- 項目鍵含 `.`、`{`、`}`、換行的拒收並回饋（殼與前端都用點分路徑查值、區段綁定成佔位符）。
- 同名的第二個人：鍵相同就是同一項目，GM 新增同名者會併成一項——列已知限制，協定請 GM 用可區分的名字（「守卫甲」）。
- `_序` 維護與輸入裡底線鍵的丟棄、序列補位、空集合保留，見第 1 節。
- 觸發條件 `contains` 指到集合時，比對項目鍵與項目內的值（現在指到分支一律落空）。

### 5. 重構契約（`refactor_ai/`）
- `INTERFACE_SHELL_COPY_RULES`：「清單整份一個字串」改為判準＋區段寫法：**卡的格式裡一筆一筆重複同一種寫法的清單（YAML 序列、重複的標籤）一律做成集合**——有名字可當身分的做具名物件、沒有的做陣列；項目格式寫成區段模板、照抄卡原文。不重複固定寫法的自由文字照舊是文字欄。
- `INTERFACE_STATE_RULES`／`INTERFACE_UPDATE_RULES`：STATE 允許集合；RULES 對集合本身給 `kind: list`，物件項目的每個欄位給 `集合.*.欄位`、純量項目給 `集合.*` 萬用規則，一律 `inject: turn`（接管桌 `incremental_by_refactor`，沒規則的葉子 GM 看不到；依形狀推定的文字欄預設 snapshot 也會在非對齊回合隱藏）；GUIDE 講每個欄位值的寫法與第 3 節的報法，不再寫縮排。
- 驗證（`result_parse.rs` `placeholders_complete`，區段解析放新檔 `refactor_ai/shell_sections.rs`）：區段成對、不巢狀；`{{#P}}` 的 P 是 STATE 的物件或陣列且有 `kind: list` 規則；區段內 `{{欄位}}` 都有 `P.*.欄位`、`{{.}}` 有 `P.*` 萬用規則且每個項目都有該欄位；缺規則判失敗（與現行全有或全無一致），不在套用時代補；`{{@key}}` 只在具名集合、`{{.}}` 只在純量項目。`kind: list` 的葉子佔位符只准出現在行內集合 `[…]` 裡（既有「集合片段」功能）；判失敗只限「重複同一種寫法的清單仍做成一整行字串」：`kind: list` 規則的葉子佔位符獨佔一行（不在行內集合裡）就失敗；不是 `kind: list` 的多行文字欄（自由文字、正文類）照舊收，不誤擋。失敗整條不套用，與現行「四塊對不上就回 None」同一套嚴格度；失敗訊息指出是哪個集合、什麼原因（區段不成對、缺萬用規則、項目缺欄位、整行字串清單……），經 `RefactorExpandOutcome.error` 回前端失敗清單。前端合併多條介面時（`refactor-review.ts`）也認區段：集合要是物件或陣列且有規則。`normalize_interface_paths` 把集合整支當一片葉子（項目不攤平、空集合不消失），集合本身與項目萬用規則不當懸空規則剔掉、跟著別名折疊。
- 套用（`refactor/`）：`interface.rs` 的 `shell_placeholders` 認區段（區段內路徑換成 `P.*.欄位` 參與別名判定）；套用時產生並寫入 `Mechanism.collections`，重建樹後依 STATE 的 JSON 順序補 `_序`（產生描述與補序的函式放 `mechanism/collection.rs`，`refactor/apply.rs` 只加呼叫）。`value_types` 不再記集合內的路徑（型別看描述）。撤銷：`receipts.rs` 的 `MechanismUndo` 照 `value_types`／`display_formats` 的做法，套用前把 `collections` 整份原表（含空表）記進同一筆、撤銷時寫回——否則撤銷後樹與規則回到舊字串清單、描述卻還是新集合，GM 整串 replace 會被形狀檢查拒收。

### 6. list_keys 去留：整組刪除〔D 已審：Sol、Grok 同意〕
刪除與包 4 的驗證（擋下舊式字串清單）同一包進 main，不留「還產得出字串清單、校正卻已刪」的中間態。
集合的鍵名在骨架裡、GM 不再寫；項目物件的鍵在套用時依萬用規則折疊（第 4 節）；舊式字串清單在重構驗證就擋掉。剩下會帶 YAML 字串清單的只有本案前產的重構卡與舊桌，發佈前不必相容。刪：`mechanism/list_keys/`（mod 431、scan 269、tests 525 行）、`Mechanism.list_key_seeds`、`resolve_list_key_seeds` 與 `chat_assembly.rs` 的載入、`apply.rs` 的 `BatchKeys`／`record_list_keys`、`RecordKind::Ignored` 說明裡的校正那句；`hint.rs` 與 `list_refusal` 的清單措辭改成集合版。

### 7. 不做／範圍外〔模型判斷·未裁決〕
- 舊桌、舊重構卡（字串清單）不搬遷；它們續聊照舊可玩，只是失去鍵名校正。
- 行內集合片段 `[{{x}}]`（值是「a, b」字串）維持現狀。
- 項目內巢狀清單。
- 重跑重構沿用目前值（`rebuild_state_fields` keep_current）時，舊桌字串清單會留在樹上、新殼的區段填不出來——屬舊桌，不處理。
- 重跑重構時「既有狀態樹」段把集合項目攤成 `在場人物.林远.身份` 這種葉子路徑列給 AI，AI 可能照抄成具體路徑；驗證會擋下不合格的產物。
- 區段標記在 YAML 區要獨佔一行只靠提示詞要求，後端不驗（後端不知道哪些標籤是 YAML 容器）。
- 沿用目前值重建樹時，已有 `_序` 的項目與新補的項目可能同名次，同名次依名字排。
- 網頁版：`web/src` 不引用 `refactor-shell.ts` 也不跑接管機制（已 grep），不受影響。

## 驗收
- 單元：區段展開與既有填值組合（北境驿站骨架填出來與原卡開場白的狀態區塊逐位元相同）；值含引號／換行／`{{…}}` 不被二次解讀；集合 insert／replace／remove／move、序列補位、序列超過 10 項照數值排序、整項 replace 保序（含夾帶 `_序` 被丟棄）、同批兩筆 insert 依序、跨集合 move 拒收且來源不動、未知欄位與祖先整份替換拒收、字形折疊；初始空集合→新增、清空→存檔重載→新增；「目前狀態」印空集合與照 `_序` 排；驗證正反例（含自由文字多行欄不誤擋、失敗訊息指名集合）；套用介面後撤銷，`collections` 與樹、規則一起回到套用前（回歸測試，包 4）。
- 測試通道零 AI：真模型重構北境驿站（新產物）→ 假 GM 腳本多回合（改單欄、進場、離場、改名、清空、寫錯字形）→ 檢查殼文字與介面每人 7 欄。測試通道排在另兩個子代理用完之後。
- 真模型（Haiku）續聊 5 回合：GM 只報變動欄位，介面不少欄、不重複人。
