# 免費玩家零門檻開始：OpenRouter 一鍵連接 → 動態穩定免費 → 推薦／限時免費模型

本檔存放 [free-player-onboarding](../tasks/free-player-onboarding.md) 的正式規格。2026-09-09 重新整理自舊 `easy-pay-onboarding` 與 `ai-connection-provider-panels`；目標不是只做到「免費第一句」，而是讓一般玩家在不懂 API key、model id、provider 與高中低 tier 的前提下，長期也能得到實用的免費對話體驗。

實作狀態（2026-09-18）：動態 `stable_free`、穩定前兩名 UI、限時／實驗性推薦、§15 新限免提示與舊 `smart_free` 遷移均已完成並 commit 到 `plan/free-player-onboarding`；目前待實機驗收。

因此本案改成三個可獨立驗收、但產品價值逐步完整的階段：

1. **OpenRouter 一鍵連接與免 key**：先消除 API key 與付款門檻，確保玩家可以送出第一句。
2. **動態穩定免費模型**：App 從帳號可用的常駐免費模型中，優先依角色扮演排行挑第一名；抓不到 RP 排行時退七日熱門，再退其他合格穩定模型。每次送出只送第一名一支，不做靜默 fallback。
3. **推薦模型＋限時免費發現**：設定頁顯示穩定前兩名（第一名自動、第二名可手動切換）與高上限限時／實驗性免費模型，並提供可關閉的新限免提示；限時模型只有玩家明確選擇才會使用。

## 產品目標

新玩家不需要先知道 API key、model id、provider、best／balanced／fast 是什麼，也不需要先付款。正常路徑應該是：

```text
打開 Table Tavern
→ 進入桌面／範例桌
→ 需要 AI 時按「連接 OpenRouter」
→ 瀏覽器登入或註冊 OpenRouter並授權
→ 回到 Table Tavern
→ 直接開始對話
→ 後續由 TT 的「穩定免費」動態選擇目前排名最高的合格常駐免費模型
```

「零門檻」不等於「零外部帳號」：OpenRouter 帳號與 OAuth 授權仍存在，只是玩家不再手工建立／複製／貼上 key，也不需要在第一句話之前研究模型。

# 第 1 階段：OpenRouter 一鍵連接與免 key

## 1. 範圍

本階段只解決一件事：**從「還沒有 OpenRouter 連線」到「可以送出第一句並收到 AI 回覆」之間，不要求玩家碰 API key 或模型設定。**

### 1.1 OAuth PKCE

依 OpenRouter 開工當下的官方 OAuth PKCE 文件實作，不把歷史 endpoint／參數當永遠不變的常數。預期流程：

1. App 建立 PKCE verifier／challenge 與 `state`。
2. 用系統瀏覽器開 OpenRouter 授權頁。
3. 玩家登入／註冊並核准 Table Tavern。
4. callback 回到本機 App。
5. App 以授權碼交換可用 API key。
6. key 寫入現有 `api_keys["openrouter"]` 本機儲存；不另造帳號系統或後端。

必須驗證 `state`，取消、逾時、callback 失敗與交換 key 失敗都要能安全返回，不留下半套連線狀態。

### 1.2 免費 bootstrap：暫時使用 `openrouter/free`

第 1 階段**不做模型推薦或智慧選模**。目前先以 OpenRouter 官方的 `openrouter/free` 免費路由作為 bootstrap，目的只有讓玩家在 OAuth 後不選模型也能立刻送出第一句。

為了不動現有 tier 架構，最小相容策略是：

- 新安裝／沒有明確自訂 OpenRouter 模型時，讓 API 的 `best`／`balanced`／`fast` 都能解析到 `openrouter/free`；實作可採「第一次連線時填入既有 `tier_models`」或「resolver 對空值給 bootstrap fallback」，開工時以最少改動與最好測試性二選一。
- `gm_tier` 與角色卡既有 tier 語意不改。
- 已有明確 OpenRouter tier 設定的玩家完全不覆蓋。
- 已有 BYOK OpenRouter key 的玩家也不強迫重跑 OAuth。

這一步**不宣稱 `openrouter/free` 是長期產品預設或最佳 RP 模型**。它只是第 1 階段當時的 bootstrap；後續已由 `stable_free` 取代。

### 1.3 新手入口

目前 onboarding 的「註冊 → 儲值 → 建 key → 貼 key」改成單一主動作，例如「連接 OpenRouter」。

要求：

- 主路徑不要出現 API key、endpoint、model id、高／中／低等術語。
- 不要求玩家先進「設定 → AI 連線」研究欄位；從桌面／onboarding 就能發起連接。
- OAuth 成功後直接回到可對話狀態，不再插入模型選擇步驟。
- 手動貼 key 保留為次要 fallback／熟手入口，不刪功能。

### 1.4 錯誤與降級

至少處理：

- 玩家取消 OAuth。
- callback／`state` 不符、逾時、瀏覽器流程未完成。
- 網路錯誤或交換 key 失敗。
- key 取得成功但首次請求失敗。
- 免費路由暫時不可用或碰到 rate limit。

錯誤訊息只告訴玩家下一步要做什麼；不要把內部 key 或 OAuth 細節丟給一般玩家。免費路由暫時不可用時可以提供重試／稍後再試／手動選模型等出口，但不把「先付款」當唯一解法。

## 2. 第 1 階段明確不做

- 不改 Claude／Codex／Antigravity／Grok CLI。
- 不拆 provider-specific panel。
- 不移動或隱藏現有高／中／低 UI。
- 不做智慧免費模型選擇器。
- 不做推薦模型清單、限時免費清單。
- 不做 GitHub Actions 自動更新模型資料。
- 不做 App 內儲值、relay、轉售額度、付款 webhook 或地區封鎖。

## 3. 第 1 階段驗收

### 新玩家實機

用全新 config 驗收：

1. 沒碰過 API 的玩家打開 TT。
2. 不建立、不複製、不貼任何 API key。
3. 不選 model id、不配置高中低。
4. 不先付款。
5. 完成 OpenRouter 登入／註冊與 OAuth 授權後，回到 TT。
6. 能送出第一句並收到模型回覆。

### 相容性

- 既有 OpenRouter key 仍可用。
- 既有 `tier_models` 不被覆蓋。
- CLI 路線行為與 UI 無差異。
- 手動 key fallback 仍可完成連線。

### 自動測試最低項

- PKCE／`state` 驗證與錯誤路徑。
- OAuth 成功後 key 落到既有 config 的正確欄位。
- bootstrap 只填空缺，不覆蓋既有 tier。
- 未自訂 tier 時 API 三檔都能解析到免費 bootstrap。

第 1 階段完成、實機真的做到「免 key 免費第一句」後，進第 2 階段。**不能把第 1 階段的 `openrouter/free` bootstrap 當成免費玩家體驗已完成。**

# 第 2 階段：動態穩定免費模型

〔現行規格 2026-09-18。取代 2026-09-17 的「高上限冷啟動＋同次 fallback」設計；舊方針與實作稿只保留決策歷史，不再作為實作依據。〕

## 4. 定義與限制

動態穩定免費＝App 用 OpenRouter 官方資料，在「現在免費、這個帳號能用」的模型中只挑常駐穩定候選；優先採角色扮演排行最高者，沒有 RP 交集才退七日熱門，再退其他合格穩定模型。排名資料變了，背景刷新後首選就能跟著變，不靠人工寫死模型名。

限制〔作者裁決 2026-09-17〕：

- 只用 OpenRouter 官方 API，金鑰用玩家 OAuth 拿到的那把；不抓網頁、不讀玩家的網頁資料、不經 TT 自己的伺服器。
- 玩家不必做任何事：不開終端機、不先選模型。
- 自動模式不選 `stealth`、有到期日或上架未滿 7 天的模型；這些只出現在限時／實驗性推薦區，讓玩家自己決定是否切換。
- 每次送出只帶當下第一名一支；單次失敗直接回報，不在同一次請求內換模，也不因一次失敗永久改綁。
- 選模結果只來自 App 執行時的資料，規格與程式不寫死任何模型名稱或名次。

為何這樣設計：免費 RP 模型品質差異大，靜默 fallback 可能讓同一段對話中途換風格，而且玩家不一定能切回原模型。現階段優先維持風格一致；若第一名當天真的失效，設定頁仍提供第二名讓玩家手動切換。

## 5. 資料來源

三支官方 API，存在本機快取：

| 要回答的問題 | 路徑 | 用到的欄位 |
| --- | --- | --- |
| 這個帳號現在能用哪些模型 | `GET /api/v1/models/user` | `id`、`canonical_slug`、`pricing`、`architecture`、`context_length`、`expiration_date` |
| 角色扮演玩家實際在用誰 | `GET /api/v1/models?category=roleplay` | 回傳順序＝名次 |
| RP 排行無交集時的穩定退路 | `GET /api/v1/models?sort=top-weekly` | 回傳順序＝七日熱門名次 |

- `/models/user` 已套用玩家帳號的隱私設定與防護規則，帳號設定擋掉的模型不會出現。
- RP 排行用 `canonical_slug` 對上帳號清單中的免費版；七日榜用 model id 取交集。對不上就略過該項。
- 這三支都不是模型呼叫，不佔免費模型每日次數。

## 6. 排名

### 6.1 候選

全部看官方欄位，沒有人工模型白名單：

- `pricing.prompt`、`pricing.completion`、`pricing.request` 為 0 或缺省為 0。
- 輸入與輸出都支援文字，context 足以容納當次輸入與預留輸出。
- 自動穩定候選必須非 `stealth`、沒有到期日、上架至少 7 天。
- 限時／實驗性推薦可包含 `stealth` 或有未來到期日的模型，但不會被自動模式選中。

### 6.2 名次

自動穩定候選依序取：

1. 角色扮演排行（`category=roleplay`）裡與帳號可用穩定候選的交集。
2. 若不足，再依七日熱門榜（`sort=top-weekly`）補。
3. 若仍不足，再從其他合格穩定模型依可重現順序補足。

自動送出只使用第 1 名。設定頁最多顯示前 2 名：第 1 名代表 `stable_free` 自動模式，第 2 名供玩家在首選失效時手動 pin。內部仍可算出前三名，作為日後「連續失敗才詢問是否換備用」的底座，但目前不會自動送出第 2、3 名。

### 6.3 不分高中低

`stable_free` 下三檔共用同一個動態首選。免費模型每次呼叫都算一次每日次數，換小模型省不到次數。

## 7. 送出

穩定免費（自動）每次呼叫（聊天、旁白、卡片重構等）都一樣：

1. 取當下合格穩定模型的角色扮演排行第一名（RP 抓不到退七日榜，再退其他合格穩定），只把這一支放進請求，不帶備援陣列。
2. 這一支失敗（下架、忙線、限流、審查）就回報這次請求失敗，玩家再送一次即可；單次失敗不算模型失效，不自動換模。
3. 碰到每日免費次數用完、402／帳號額度類錯誤就停，直接回報；這是帳號層級問題，換另一支免費模型也救不了。

為何不送備援陣列：OpenRouter 免費 RP 模型品質不穩，靜默換模會讓對話中途風格突變、玩家又不一定換得回來，現狀下「不換模型」較好〔作者裁決 2026-09-18〕。備援名次仍照算：設定頁把穩定前兩名都列出來，第一名當天失效時玩家可手動改用第二名（兩支同時掛的機率遠低於一支）〔作者裁決 2026-09-18〕。deferred：連續 N 次失敗自動跳視窗問玩家要不要換備用、玩家選了備用後至少一天不自動換回。

## 8. 目前模型

- 目前模型＝當下合格穩定模型裡角色扮演排行第一名（RP 抓不到退七日榜，再退其他合格穩定）。
- 只在背景刷新（≤12 小時）拿到新排行、第一名真的換人時才換；不因單次失敗、也不在同一次請求內換。
- pins 記錄每桌最近一次實際回話的模型，只供設定頁「目前使用（預測）」顯示與到期提醒，不再決定選哪支。

為何：品質不穩的免費模型，同一天在對話中途換文風的體感很差；把選模綁在排行、只在背景刷新才可能換人，玩家不會每句都被換掉。

## 9. 更新時機

- OAuth 完成後 warm 一次；之後 App 啟動與背景流程檢查快取，資料超過 12 小時就重抓，不擋聊天。
- 三份資料各自快取、各自更新。RP 排行抓不到或沒有合格交集就退七日榜；七日榜也沒有就退其他合格穩定模型。帳號模型清單若暫時抓不到，沿用仍有效的舊快取；沒有可用 catalog 時才回報目前沒有可用免費模型。
- 新資料格式驗證通過才整份替換，壞資料不覆蓋好資料。

## 10. 玩家看到什麼

設定頁原本的模型設定位置：

```text
模型
穩定免費
● Model A　角色扮演熱門免費模型
  目前使用（預測）：Model A
○ Model B　角色扮演熱門免費模型（第一名失效時可手動改用）

限時／實驗性免費
○ Model X　限時免費・推薦理由：…
○ Model Y　實驗性免費・推薦理由：…

○ 手動選擇模型
```

- 第 3 階段起，新玩家 OAuth 完成後預設 `api_model_mode=stable_free`。舊 `smart_free` 是 migration-only alias，既有玩家讀寫設定時遷移到 `stable_free`；手動／recommended 與 CLI 路線不改。
- 「穩定免費」推薦本身就是自動模式 radio，不再另外顯示「智慧免費」radio。畫面上的 Model A 只是當下 RP 排名推得的首選；玩家選「穩定免費」不會把 Model A 永久寫入 tier。
- 穩定免費（自動）每次送出只送當下 RP 穩定第一名一支，不送備援陣列；備援名次照算，只用於設定頁列出前兩名（第一名自動、第二名供手動改用）。
- 限時、`stealth`、有到期日的模型不會自動選；玩家只有明確點該推薦時才固定使用。

## 11. 已知限制

- RP 與七日熱門都是使用度／熱度訊號，不是中文角色扮演品質保證。
- 免費版可能和同系列付費版在量化、context 或 provider 路由上有差異。
- 每日免費次數整個帳號共用，換模型救不了。
- 新上架或短期免費模型刻意不進自動穩定候選，只會出現在限時／實驗性推薦區。

## 12. 第 2 階段驗收

- 全新設定＋真 OAuth（授權由使用者本人按）：不選模型送出第一句，收到回覆；`api_model_mode=stable_free`，實際請求使用當下合格穩定第一名。
- 穩定免費只送一支、不送備援陣列：第一支不能用就回報這次請求失敗，玩家再送一次（deferred：連續失敗才問玩家換備用）。
- 設定頁穩定區最多列前兩名；第一名 radio 代表自動模式，第二名可手動切成 `recommended`；限時／實驗性模型另列在後面。
- 固定測試資料可重現：免費／文字／context 篩選、穩定條件、RP → weekly → available 排序、限時模型不進自動路徑、只送單支、舊 `smart_free` 遷移到 `stable_free`、資料快取失敗沿用舊值。
- 手動選模型的玩家、CLI 路線行為不變。

# 第 3 階段：推薦模型＋限時免費發現與提示

## 13. 目標

第 3 階段除了讓玩家知道「現在有哪些值得玩的免費模型」與「出現值得注意的新限免時，要不要告訴他」，也把原第 2 階段的「智慧免費」正式收斂成**動態穩定免費預設**。自動路徑只選常駐穩定模型；高上限限時／實驗性模型改成發現後由玩家明確選擇。

這一階段把既有選模資料轉成**可理解、可選擇、可關閉的發現介面**，而不是再增加設定負擔。

一般玩家可以看到兩類內容，兩者要明確分開，且 UI 順序固定為穩定在前、限時在後：

1. **穩定免費模型**：非 stealth、沒有到期日、上架至少 7 天的免費模型中，畫面最多顯示前兩名；第一名同時就是 `stable_free` 自動模式的控制，第二名供首選失效時手動改用〔RP 方針·使用者裁決 2026-09-18〕。
2. **限時／實驗性免費模型**：高上限候選（`stealth/*` 或有 `expiration_date` 的免費 preview／試驗模型）。即使只剩一天也仍值得推薦；但它們只供玩家明確選擇，不加入自動 stable fallback。

## 14. 推薦清單

限時／實驗性區沿用既有高上限分類；不使用已廢棄的能力分＋角色扮演 RRF 合成設計。穩定項目由角色扮演排行挑選（見下），同時代表動態自動模式。

- 清單採 **2 + N**：穩定區最多顯示 2 支（第一名自動＋第二名手動備援），加上當下所有值得推薦的限時／實驗性高上限模型；穩定區排在限時區前。
- 限時區不限制總支數。若同一時期真的有多支強力限時免費模型，就全部列出；沒有就只剩穩定那區。
- 穩定免費畫面首選取通過硬門檻後**角色扮演排行**（官方 `GET /api/v1/models?category=roleplay`，回傳順序＝名次，走 `canonical_slug` 對上帳號的 `:free` 版）最高的一支〔RP 方針·使用者裁決 2026-09-18〕；若無交集再退七日熱門榜（`top-weekly`），再沒有就用其他合格穩定模型。畫面列出同一來源的前兩名（RP → weekly → 其他 stable，不重複）；自動模式只送第一名一支、不送備援陣列，第二名供玩家手動改用。限制不變：只走官方 API、不爬網頁、不偷抓玩家網頁資料。
- 限時／實驗性免費區沒有合格推薦時，仍保留該區並顯示空狀態，例如「目前沒有推薦的限時免費模型」。
- 顯示模型名稱、類型、是否為目前使用中的模型，以及必要的期限提示。
- **推薦模型直接用 radio 式單選項目點選**：穩定項目被選中代表 `stable_free` 動態模式，不 pin 當下顯示的模型；限時／實驗性項目被選中才代表固定該具體模型。推薦區不提供手填欄位，也不顯示下拉式選單。
- 每支限時／實驗性推薦模型**最好附一個簡短的「推薦理由／判斷依據」**，讓同時出現多支強力限免時玩家能判斷該選哪支。推薦理由屬顯示資訊，不改變本節的入選規則；可用資料來源與呈現欄位在串接 OpenRouter 真資料時確認。
- 推薦理由改採**即時可判斷的模型身分／試驗型態訊號**，不依賴七日使用排行、RP 排名、第三方能力分等需要時間累積的資料。短命的強力測試模型一出現就應能被解釋，不能等它快下架才有分數。
- 推薦理由的候選訊號：
  1. **明確供應商＋preview／experimental／beta／alpha／限時到期**：若 model id namespace、名稱或官方欄位能明確辨認供應商，可顯示例如「Google 的限時 Preview 模型」「大型供應商的新測試版本」。只有來源明確時才寫供應商，不自行猜匿名模型身分。
  2. **`stealth/*`**：顯示「新出現的匿名測試模型」／「匿名高上限試驗模型」。stealth 身分刻意隱藏，不能寫成某一家大廠；若同時很新、context 大，可補充「剛上架」「長上下文」等客觀特徵。
  3. **短期期限**：有可信近期 `expiration_date` 時，可直接把「限時測試／預計至 YYYY-MM-DD」當成推薦理由的一部分；越短命反而越值得及早提醒。
  4. **新上架**：`created` 只用來產生「剛上架／新測試」這類理由，不顯示開始日期，也不把新舊本身當品質分數。
  5. **context 長度**：只當輔助理由，例如「256K 長上下文」，尤其適合用來解釋為什麼這支看起來像高規格試驗模型；不把 context 當品質排名。
- 這幾條理由只用在**限時／實驗性**區：這裡不把 Roleplay/Fiction 使用排行、Artificial Analysis Intelligence Index 等需要時間累積的分數當推薦理由，因為短命測試模型一出現就要能解釋，不能等它快下架才有分數。（穩定保底另一回事：它本來就是常駐模型，直接以角色扮演排行挑選，標示「角色扮演熱門免費模型」。）
- 上述理由只幫玩家比較**已經入選**的限時／實驗性模型；不重新引入任何評分式入選規則。
- **不顯示開始日期**。`created` 代表模型在 OpenRouter 的上架時間，不等於免費活動開始時間；最多只能拿來判斷「新上架」，不能當活動起日顯示。
- `expiration_date` 距今 **90 天內**時，視為值得呈現的近期期限，文案使用「預計至 YYYY-MM-DD」。
- `expiration_date` 缺失，或日期遠到不適合視為可靠活動期限時，一律合併顯示為「實驗性免費・可能隨時結束」，不顯示那個遠期日期。
- 距到期不到 **72 小時**時仍保留在推薦清單，另加「即將到期」警告；珍貴的高上限模型即使只剩一天也值得讓玩家知道。

## 15. 新模型／限免提示

這裡**不要**變成「OpenRouter 每新增一個免費模型就跳窗」。通知的主要目的，是在值得追的限時／實驗性強力模型出現時提醒玩家趕快試；穩定免費模型通常不需要主動通知。

**v1 範圍〔作者裁決 2026-09-18〕：主動通知只做一件事——新的高上限限時／實驗性免費模型進入推薦清單就跳一次。** 其餘三種留作後續另做，本輪不實作：

- 某個既有模型後來出現官方可驗證的近期免費期限。
- 穩定免費的動態首選因排行變動而更換。
- 已推薦（但非目前在用）的限時模型進入到期前 72 小時。

（目前穩定自動路徑不會主動選有到期日的模型；既有舊 pin 若仍留下到期資訊，既有提醒機制可照常處理。）

提示應採非阻塞式 banner／toast／輕量彈窗，至少提供：

```text
發現新的推薦免費模型
Model X 現在可免費使用。

[下一個新對話改用] [查看] [略過]
```

並提供本機記錄的：

- 對這一則通知「不再顯示」。
- 必要時可整體關閉「新免費模型提醒」。

`stable_free` 模式只在穩定候選間依即時排名自動選模；`recommended`／手動模式只提示，不得偷偷切換。

第一版不需要 push service。App 啟動／背景 TTL 刷新後，比對上次看過的推薦清單即可（背景刷新換到新快取時發事件，前端據此重查）。

首次啟動、換 OpenRouter 帳號、或還沒有任何「看過」基準時：**靜默把當下限時推薦建為基準、不對既有清單跳提示**，只提醒之後才真正進入清單的高上限限時／實驗性模型〔使用者裁決 2026-09-18〕。即使當下限時清單為空，也要建立空 baseline，避免第一支之後新出現的限時模型被吞掉。手動／recommended 玩家同樣做背景刷新與提示；只有 `stable_free` 會自動選模。

## 16. 第 3 階段 UI 原則

這一輪仍**不做整個 provider 設定頁重構**。只在 OpenRouter 的一般玩家路徑上增加必要的模型發現介面。

可以呈現為：

```text
穩定免費
● Model A　角色扮演熱門免費模型
  目前使用（預測）：Model A
○ Model B　角色扮演熱門免費模型（第一名失效時可手動改用）

限時／實驗性免費
○ Model X　限時免費・預計至 2026-09-30　推薦理由：…
○ Model Y　實驗性免費・可能隨時結束　推薦理由：…
○ Model Z　即將到期・預計至 2026-09-19　推薦理由：…
```

沒有值得推薦的限時／實驗性模型時：

```text
穩定免費
● Model A　角色扮演熱門免費模型
○ Model B　角色扮演熱門免費模型（第一名失效時可手動改用）

限時／實驗性免費
目前沒有推薦的限時免費模型
```

玩家點「穩定免費」時，前端只把 `api_model_mode` 設為 `stable_free`；畫面當下顯示的第一名不寫進 tier，下一次送出仍重新依 RP 排名挑第一名一支送出（不送備援陣列）。玩家點穩定第二名、或限時／實驗性推薦後，前端才把 `api_model_mode` 設為 `recommended`，並把 OpenRouter 的 `best`／`balanced`／`fast` 三個既有 tier 都指向該模型；後端仍走既有手動 model resolver。推薦模式不顯示三個手填欄；切回「手動選擇模型」才重新顯示進階手填。

## 17. 第 3 階段明確不做

- 不改任何 CLI provider 的設定方式。
- 不把 Claude／Codex／Antigravity／Grok 改成 provider-specific panel。
- 不為了模型清單刪除既有 tier contract 或做大型 config migration。
- 不做 App 內儲值或任何自營付費服務。
- 不做需要蒐集玩家聊天內容的個人化推薦。

## 18. 第 3 階段驗收

- 免費玩家不用打開完整模型目錄，也看得懂「目前穩定免費下一輪會用誰」與「還有哪些值得試」。
- 穩定免費與限時／實驗性免費有清楚區別，且穩定區優先呈現。
- 推薦清單遵守 2 + N：穩定免費最多兩支（第一名自動＋第二名手動備援），限時／實驗性高上限模型有幾支就列幾支，不設總數上限。
- 沒有限時／實驗性推薦時，該區顯示明確空狀態，穩定免費區仍保留當下角色扮演排行最高的合格常駐前兩名（排行抓不到才退七日榜）。
- 推薦模型以 radio 單選直接點選；選中後圓圈為實心，不要求手填，也不顯示下拉選單。
- 選穩定免費後以 `api_model_mode=stable_free` 保存且不 pin 當下顯示模型；點穩定第二名或限時／實驗性推薦後才以 `api_model_mode=recommended` 保存，三個 OpenRouter tier 同步固定到同一支；選回穩定免費恢復自動只送第一名。
- 同時有多支限時／實驗性推薦時，每支最好顯示簡短推薦理由／判斷依據；理由只幫玩家比較，不改變模型是否進入推薦清單。
- 不顯示免費活動開始日期。
- 只有距今 90 天內的可信 `expiration_date` 才顯示具體日期；缺期限或遠期期限都使用同一套「可能隨時結束」文案，不猜實際撤回日。
- 距到期不到 72 小時的推薦仍留在清單，並清楚標示「即將到期」。
- 新推薦提示不是每次啟動重複出現；「不再顯示」有效且只存在本機。
- 手動選模玩家收到提示後不會被自動切換。
- `stable_free` 每次送出只送當下 RP 穩定第一名一支、不送備援陣列；單次失敗只回報不換模；限時／stealth 不會被自動帶入。
- RP 排名抓不到或沒有合格交集時能退 weekly／available；單次模型請求失敗仍只回報，不自動切到下一支。
- 舊 OpenRouter 熟手設定與全部 CLI 路線不受影響。

# 延後另案

以下全部從本案移出：

- `ai-connection-provider-panels`：各供應商專屬下半頁、CLI 是否顯示單模型或預設模型、高中低 UI 搬家。
- App 內儲值／自營 relay／金流／地區阻擋。
- 模型推薦的自動化營運（GitHub Actions 自動排行、後端評測服務、真正 push notification 等）。
- 需要蒐集玩家對話或角色卡資料才能運作的個人化選模。

只有三個階段真的被玩家使用後，再依實際痛點決定要不要開這些案。
