# 免費玩家零門檻開始：OpenRouter 一鍵連接 → 智慧免費 → 推薦／限時免費模型

本檔存放 [free-player-onboarding](../tasks/free-player-onboarding.md) 的正式規格。2026-09-09 重新整理自舊 `easy-pay-onboarding` 與 `ai-connection-provider-panels`；目標不是只做到「免費第一句」，而是讓一般玩家在不懂 API key、model id、provider 與高中低 tier 的前提下，長期也能得到實用的免費對話體驗。

因此本案改成三個可獨立驗收、但產品價值逐步完整的階段：

1. **OpenRouter 一鍵連接與免 key**：先消除 API key 與付款門檻，確保玩家可以送出第一句。
2. **智慧免費模型**：把 `openrouter/free` 從長期預設降級成安全 fallback；TT 自己從目前真的免費且可用的模型裡選較合適的實際模型，讓「不用選模型」也能實際好用。
3. **推薦模型＋限時免費發現**：再把選擇邏輯變成玩家看得懂的推薦清單、限免提示與可控通知，而不是把模型研究丟回玩家身上。

## 產品目標

新玩家不需要先知道 API key、model id、provider、best／balanced／fast 是什麼，也不需要先付款。正常路徑應該是：

```text
打開 Table Tavern
→ 進入桌面／範例桌
→ 需要 AI 時按「連接 OpenRouter」
→ 瀏覽器登入或註冊 OpenRouter並授權
→ 回到 Table Tavern
→ 直接開始對話
→ 後續由 TT 的「智慧免費」維持一個可用、較合適的免費模型
```

「零門檻」不等於「零外部帳號」：OpenRouter 帳號與 OAuth 授權仍存在，只是玩家不再手工建立／複製／貼上 key，也不需要在第一句話之前研究模型。

---

# 第 1 階段：OpenRouter 一鍵連接與免 key

## 1. 範圍

本階段只解決一件事：**從「還沒有 OpenRouter 連線」到「可以送出第一句並收到 AI 回覆」之間，不要求玩家碰 API key 或模型設定。**

### 1.1 OAuth PKCE

依 OpenRouter 開工當下的官方 OAuth PKCE 文件實作，不把歷史 endpoint／參數當永遠不變的常數。預期流程：

1. App 建立 PKCE verifier／challenge 與 `state`。
2. 用系統瀏覽器開 OpenRouter 授權頁。
3. 玩家登入／註冊並核准 Table Tavern。
4. callback 回到本機 App。
5. App 以授權碼交換可用 API key。
6. key 寫入現有 `api_keys["openrouter"]` 本機儲存；不另造帳號系統或後端。

必須驗證 `state`，取消、逾時、callback 失敗與交換 key 失敗都要能安全返回，不留下半套連線狀態。

### 1.2 免費 bootstrap：暫時使用 `openrouter/free`

第 1 階段**不做模型推薦或智慧選模**。目前先以 OpenRouter 官方的 `openrouter/free` 免費路由作為 bootstrap，目的只有讓玩家在 OAuth 後不選模型也能立刻送出第一句。

為了不動現有 tier 架構，最小相容策略是：

- 新安裝／沒有明確自訂 OpenRouter 模型時，讓 API 的 `best`／`balanced`／`fast` 都能解析到 `openrouter/free`；實作可採「第一次連線時填入既有 `tier_models`」或「resolver 對空值給 bootstrap fallback」，開工時以最少改動與最好測試性二選一。
- `gm_tier` 與角色卡既有 tier 語意不改。
- 已有明確 OpenRouter tier 設定的玩家完全不覆蓋。
- 已有 BYOK OpenRouter key 的玩家也不強迫重跑 OAuth。

這一步**不宣稱 `openrouter/free` 是長期產品預設或最佳 RP 模型**。它只是第 2 階段尚未完成前的安全底線。

### 1.3 新手入口

目前 onboarding 的「註冊 → 儲值 → 建 key → 貼 key」改成單一主動作，例如「連接 OpenRouter」。

要求：

- 主路徑不要出現 API key、endpoint、model id、高／中／低等術語。
- 不要求玩家先進「設定 → AI 連線」研究欄位；從桌面／onboarding 就能發起連接。
- OAuth 成功後直接回到可對話狀態，不再插入模型選擇步驟。
- 手動貼 key 保留為次要 fallback／熟手入口，不刪功能。

### 1.4 錯誤與降級

至少處理：

- 玩家取消 OAuth。
- callback／`state` 不符、逾時、瀏覽器流程未完成。
- 網路錯誤或交換 key 失敗。
- key 取得成功但首次請求失敗。
- 免費路由暫時不可用或碰到 rate limit。

錯誤訊息只告訴玩家下一步要做什麼；不要把內部 key 或 OAuth 細節丟給一般玩家。免費路由暫時不可用時可以提供重試／稍後再試／手動選模型等出口，但不把「先付款」當唯一解法。

## 2. 第 1 階段明確不做

- 不改 Claude／Codex／Antigravity／Grok CLI。
- 不拆 provider-specific panel。
- 不移動或隱藏現有高／中／低 UI。
- 不做智慧免費模型選擇器。
- 不做推薦模型清單、限時免費清單、遠端推薦 manifest。
- 不做 GitHub Actions 自動更新模型資料。
- 不做 App 內儲值、relay、轉售額度、付款 webhook 或地區封鎖。

## 3. 第 1 階段驗收

### 新玩家實機

用全新 config 驗收：

1. 沒碰過 API 的玩家打開 TT。
2. 不建立、不複製、不貼任何 API key。
3. 不選 model id、不配置高中低。
4. 不先付款。
5. 完成 OpenRouter 登入／註冊與 OAuth 授權後，回到 TT。
6. 能送出第一句並收到模型回覆。

### 相容性

- 既有 OpenRouter key 仍可用。
- 既有 `tier_models` 不被覆蓋。
- CLI 路線行為與 UI 無差異。
- 手動 key fallback 仍可完成連線。

### 自動測試最低項

- PKCE／`state` 驗證與錯誤路徑。
- OAuth 成功後 key 落到既有 config 的正確欄位。
- bootstrap 只填空缺，不覆蓋既有 tier。
- 未自訂 tier 時 API 三檔都能解析到免費 bootstrap。

第 1 階段完成、實機真的做到「免 key 免費第一句」後，進第 2 階段。**不能把第 1 階段的 `openrouter/free` bootstrap 當成免費玩家體驗已完成。**

# 第 2 階段：智慧免費模型

## 4. 目標

第 2 階段是本案從「能玩」走到「實用」的核心。

一般玩家應該只需要知道一個概念：

```text
智慧免費（推薦）
目前實際使用：<某個免費模型>
```

玩家不需要自己追蹤哪個模型剛變免費、哪個免費版下架、哪個模型比較適合 TT。TT 應該能定期取得 OpenRouter 的客觀模型狀態，再依自己的選擇規則解析成一個實際 model id。

`openrouter/free` 從這一階段開始只保留為**最終安全 fallback**，不再是 TT 自己認定的長期首選模型。

## 5. 「智慧免費」不是自動亂換模型

智慧免費是一種**模型選擇模式**，不是「每次 App 啟動就把使用者設定改寫成另一個 model id」。

必須遵守：

- 玩家若明確手動選過模型，手動選擇永遠優先；TT 不得在背景覆蓋。
- 動態選出的實際 model id 不應被偽裝成玩家永久手動設定；開工時應盤點現有 config／resolver，選擇能明確區分「智慧模式」與「手動 model id」的最小相容做法。
- **既有正在進行的對話／桌局，不得只因推薦資料刷新而靜默換模型。** 新推薦至少等下一個自然綁定點（例如新對話／新桌局／玩家明確切換）才生效。
- 只有目前模型真的不可用、下架或請求失敗到需要降級時，才允許在同一對話走 fallback；這是故障復原，不是日常自動換模。

如果現有架構沒有可持久化的「對話所用模型」，開工前要先確認最小 pinning 邊界；不能為了省事讓每次 request 都重新挑一個模型。

## 6. 資料來源與選模分工

### 6.1 OpenRouter catalog：回答「現在真的能不能用」

沿用現有 `/api/v1/models` 或開工當下官方等價資料源，只讀選模真正需要的最小 metadata，例如：

- model id／顯示名。
- 目前價格是否為 0。
- context／能力／支援參數等必要相容性資料。
- 官方若提供可依賴的下架／到期欄位，可用於排除即將失效候選，但不得猜日期。

Catalog 是**客觀現況**，不是 TT 的主觀推薦分數。

### 6.2 TT 遠端選模 manifest：回答「我們優先選誰」

第 2 階段即可加入一份很小的公開靜態 manifest，放在 Table Tavern 可控的公開來源，不需要自營 API server。它的目的不是做 UI，而是讓 TT 不必等 App 發新版才能調整免費模型優先級。

第一版至少能表達：

- schema/version。
- `updated_at`。
- 智慧免費模型的優先順序或候選集合。
- 暫時停薦／排除。
- 必要時的最低 App 版本或簡單相容條件。

OpenRouter catalog 與 manifest 必須交叉驗證：**manifest 說推薦，不代表模型現在仍免費；catalog 說免費，也不代表 TT 就一定推薦。**

### 6.3 發行版內建 fallback policy

App 內必須內建一份最小安全 policy，避免遠端 manifest 失效就無法選模。

建議降級順序：

```text
有效遠端 policy + 目前 catalog
→ 最後一次成功快取的 policy + 目前／快取 catalog
→ 發行版內建安全候選
→ openrouter/free
```

任何一層資料損壞、斷網或格式不相容，都不能阻擋聊天。

## 7. 更新與快取

智慧免費不需要每次開 App 都同步阻塞等待網路。

要求：

- App 啟動可檢查快取是否過期；仍新鮮就直接使用。
- 過期時在背景刷新，聊天不能被推薦資料請求卡住。
- 第一版可採約 12～24 小時等級的合理 TTL；實作前依現有啟動流程與網路層決定具體值，不把這個區間視為 API 契約。
- 成功取得新 policy／catalog 後先驗證，再原子替換本機快取；壞資料不能覆蓋最後一份好資料。
- 不需要上傳聊天內容、角色卡或玩家偏好來做選模。

## 8. 選模規則

第一版不要做一套看似精準、實際無法驗證的複雜「AI 品質分數」。

建議採保守 pipeline：

1. 從 catalog 取得目前免費且可用的候選。
2. 排除明顯不符合 TT 文字聊天需求或已知不穩定／停薦的模型。
3. 套用 TT manifest 的優先順序。
4. 沒有任何策展候選時，再用 catalog 的客觀條件做保守 fallback。
5. 全部失敗才回 `openrouter/free`。

未來若真的有足夠資料再增加速度、context、OpenRouter 排名或其他客觀訊號；**不要第一版就假裝能從 benchmark 自動推導「最適合 RP」。**

## 9. 第 2 階段 UI 原則

這一階段仍然不做完整模型商城或推薦清單。

一般玩家只需要看得到：

```text
模型
● 智慧免費（推薦）
  目前使用：Model A

○ 手動選擇模型
```

實際 UI 要配合現有設定頁，不為此順手重做 provider-specific panel 或高中低系統。

若目前產品路徑甚至不需要玩家看到這一欄，智慧免費也可以先作為新玩家的內部預設；但設定頁至少要有清楚出口讓熟手切回手動，不得把自動策略做成無法關閉的黑箱。

## 10. 第 2 階段驗收

- 全新玩家 OAuth 完成後，不研究模型也會進入智慧免費模式。
- 有有效 catalog／policy 時，TT 解析到一個**具體、當下免費**的模型，而不是長期直接把 `openrouter/free` 當首選。
- 玩家明確手動選過的模型不被自動覆蓋。
- policy／catalog 在背景刷新時，正在進行的對話不會因此突然換模型。
- 當首選模型下架／不可用時，會依候選順序降級；最後仍可退回 `openrouter/free`。
- 遠端 manifest 掛掉、斷網、cache 壞掉時仍能聊天。
- 選模測試使用固定 fixtures，可重現「免費／非免費、停薦、資料過期、模型消失、fallback」等結果，不依賴測試當下 OpenRouter 線上狀態。
- CLI 路線與既有手動 OpenRouter 設定不受影響。

完成這一階段後，才算真正達到「免費玩家不用懂模型也有實用預設」。

# 第 3 階段：推薦模型＋限時免費發現與提示

## 11. 目標

第 2 階段已經替一般玩家自動處理選模；第 3 階段才解決「玩家想知道現在有哪些值得玩的免費模型」以及「出現值得注意的新限免時，要不要告訴他」。

這一階段把既有選模資料轉成**可理解、可選擇、可關閉的發現介面**，而不是再增加設定負擔。

一般玩家可以看到兩類內容：

1. **Table Tavern 推薦免費模型**：針對 RP／長對話等 TT 使用情境人工策展。
2. **限時免費模型**：原本付費、活動期間免費或具有明確免費期限／免費活動的模型；只有資料來源足夠可信時才標示。

## 12. 推薦清單

可沿用第 2 階段的 manifest，擴充必要的人類可讀欄位，例如：

- 顯示名稱。
- 短理由，例如「角色扮演」「速度快」「長上下文」。
- 是否為智慧免費首選。
- 限免標籤。
- 有可信官方證據時才附 `expires_at`。

OpenRouter catalog 仍負責驗證「現在是否存在、現在是否免費」；遠端 manifest 只負責 TT 的策展與說明。

## 13. 新模型／限免提示

這裡**不要**變成「OpenRouter 每新增一個免費模型就跳窗」。通知只應對玩家真的可能在意的事件出現，例如：

- TT manifest 新增一個高優先級推薦免費模型。
- 某個值得注意的付費模型出現官方可驗證的限時免費活動。
- 智慧免費的首選已經換成明顯不同的新推薦，且值得告知玩家。

提示應採非阻塞式 banner／toast／輕量彈窗，至少提供：

```text
發現新的推薦免費模型
Model X 現在可免費使用。

[下一個新對話改用] [查看] [略過]
```

並提供本機記錄的：

- 對這一則通知「不再顯示」。
- 必要時可整體關閉「新免費模型提醒」。

智慧免費模式可以在**下一個自然綁定點**自動採用新的首選；手動模式只能提示，不得偷偷切換。

第一版不需要 push service。App 啟動／背景 TTL 刷新後，比對最後看過的 manifest revision／announcement id 即可。

## 14. 第 3 階段 UI 原則

這一輪仍**不做整個 provider 設定頁重構**。只在 OpenRouter 的一般玩家路徑上增加必要的模型發現介面。

可以呈現為：

```text
目前使用
智慧免費
實際模型：Model A

Table Tavern 推薦免費模型
- Model A　推薦：角色扮演
- Model B　推薦：速度快

限時免費
- Model C　免費至 2026-xx-xx（只有可信期限才顯示）
```

玩家選一個模型後如何映射到現有三 tier，開工時以「不靜默覆蓋熟手既有自訂」為最高原則；不為了這個清單順手重做高中低模型系統。

## 15. 第 3 階段明確不做

- 不改任何 CLI provider 的設定方式。
- 不把 Claude／Codex／Antigravity／Grok 改成 provider-specific panel。
- 不為了模型清單刪除既有 tier contract 或做大型 config migration。
- 第一版不做 GitHub Actions 自動策展；推薦優先級與通知是否值得顯示仍由人工策展。
- 不做 App 內儲值或任何自營付費服務。
- 不做需要蒐集玩家聊天內容的個人化推薦。

## 16. 第 3 階段驗收

- 免費玩家不用打開完整模型目錄，也看得懂「目前智慧免費實際用了誰」與「還有哪些值得試」。
- 推薦免費與限時免費有清楚區別。
- 限時免費沒有可靠證據就不標期限、不猜。
- 新推薦提示不是每次啟動重複出現；「不再顯示」有效且只存在本機。
- 手動選模玩家收到提示後不會被自動切換。
- 智慧免費玩家的新首選只在安全綁定點生效，不打斷既有對話。
- 推薦服務斷線／資料過期／推薦模型下架時，第 2 階段的智慧免費 fallback 鏈仍正常工作。
- 舊 OpenRouter 熟手設定與全部 CLI 路線不受影響。

# 延後另案

以下全部從本案移出：

- `ai-connection-provider-panels`：各供應商專屬下半頁、CLI 是否顯示單模型或預設模型、高中低 UI 搬家。
- App 內儲值／自營 relay／金流／地區阻擋。
- 模型推薦的自動化營運（GitHub Actions 自動排行、後端評測服務、真正 push notification 等）。
- 需要蒐集玩家對話或角色卡資料才能運作的個人化選模。

只有三個階段真的被玩家使用後，再依實際痛點決定要不要開這些案。
