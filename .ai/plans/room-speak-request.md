# room-speak-request：房間「請某某發言」拆成兩個功能（方案）

全篇〔模型判斷·未裁決〕。範例角色：玩家「灰鬃」（狼獸人）、「岩角」（牛獸人），NPC「老酒保巴頓」（熊獸人）。

## 0 先釐清：現在這顆鈕其實不會讓 AI 代替玩家

`GmControls` 的「請{名字}發言」只列**沒人認領**的卡，也就是 NPC，在場玩家的卡不會出現在清單裡。所以作者說的「替玩家決定讓 AI 代打」，正常情況下不會發生。回饋裡的「打斷對方、AI 代替發言」比較像是下面三件事疊在一起：

1. **字面誤導**：「請巴頓發言」在多人桌上讀起來像「請那位玩家打字」。
2. **默默打斷**：按下去會 `cancelRound`，大家已送出的行動悄悄退回草稿，畫面沒有任何提示。玩家感覺到的就是「我說到一半被打斷」。
3. **離座玩家的卡混在名單裡**：玩家離座、卡交給 GM 當 NPC 之後，這張卡會出現在選單裡，房主一按，看起來就像 AI 在替那位玩家說話。

作者「拆成兩個功能」的判斷我同意，照做（§1、§2）。另外要補一點：真正傷人的是第 2 點，不管名字改成什麼，這個問題都還在，所以 §3 一定要一起修。

## 1 房主：催促某位玩家（新功能）

**玩家會看到什麼**
- 房主故事頁的「還在等：灰鬃、岩角」那一列，每個名字變成可以點的小鈕「催一下」（這個人在線、在行動名單裡、而且還沒送出時才出現）。離線的人旁邊照現有放「交給 AI 代管」，不放催促。
- 被催的玩家：手機震動一下（瀏覽器支援才震），行動格上方出現一條「房主在等你的行動」，輸入框自動取得焦點。這條在他送出、按跳過，或回合結束時消失。只有他本人看得到，別人看不到他被催。
- 房主按下後，那顆鈕變成「已提醒」並停用 30 秒，避免連按洗版。

**按了會發生什麼**
- 送新指令 `host.nudge { round, memberId }`。伺服器驗：房主、`round` 是當前 `acting` 回合（沿用 `roundAt`）、對象在名單裡且還沒送出（pending／drafting）、在線。
- 冷卻在伺服器：重用 `member.ts` 的 `rate`，鍵＝房主＋對象，30 秒 1 次；超過回 `E_RATE_LIMITED`（帶剩餘時間），按鈕據此顯示「已提醒」。只停用按鈕擋不住多頁連按。`rate` 的計數在記憶體（`live.buckets`），房間被逐出就歸零，冷卻用途可接受。
- 通過後 `tx.toMember` 私下送對方 `vol { type: "nudged", round }`；客戶端只在 `round` 等於當前回合時顯示，換回合就清掉，晚到的舊催促不顯示。
- 回合不動，不寫進故事串，也不進事件日誌。重連之後不補送，催促本來就是當下的事。
- 不做「全部催一次」。催的對象應該是具體的人，「還在等」那一列本身已經算是群體提示。

## 2 玩家：「跳過」改名「交給 GM」〔作者裁決 2026-11-06：方向同意，按鈕字要短，用「交給 GM」〕

不另加「交給 AI 這回合」鈕（Fable 與主線一致；理由：跟跳過只差「GM 必須動他」，不值得新增整套 auto 資料格式）。

- 按鈕：行動格「跳過」改名「交給 GM」；title：「GM 可能替你的角色安排一個小動作，也可能讓他在旁觀望」。
- 伺服器與協定：不改。照舊 `action.skip` → roster `skipped` → batch `watch`（`watchReason: "skipped"`）；事件、快照、`round.resolved` 已經帶 `watchReason`。
- 草稿與旗標：沿用 skip 現況，不另立旗標。按「交給 GM」不動草稿；收回（`action.retract`）、交給 AI 代管（`delegate`）都會把 `skipped` 退回 pending／drafting；之後送出文字是另一個狀態（submitted），不會沿用「交給 GM」。
- 執行端（目前斷在這裡）：`room/run.rs` 把 batch 轉成 `PartyAction::Watch { card_id }` 時丟掉了 `watchReason`。改成 Watch 帶「交給 GM」與否（只有 `watchReason == "skipped"` 算）；`party_batch.rs` 落檔時，交給 GM 的寫新標記 `PlayerHandedToGm { name }`，其餘照舊 `PlayerWatch`。新標記的三語模板是固定句「{name} 把這回合交給 GM：可以替他安排一個符合個性的小動作，不替他說話、不替他做重大決定，也可以讓他只在旁觀望」；`turns.rs` 的 `summary_party_note` 與前端 `event-text.ts` 的標記清單一併加上。標記落在逐字稿裡，重生重派同一份派工會落同樣的標記，收回會一起撤掉。
- 提示詞例外：名單綁定當次派工，不在逐字稿裡往回找。`gm_narrate` 本來就收到當次派工的 `action_id`（＝`dispatchId`），往下傳給 `gm_instruction`；名單＝本幕事件裡 `marker == PlayerHandedToGm` **而且** `action_id` 等於當次派工的那幾格。`response.rs::party_instruction` 多收這份名單，非空才在「不要替任何真人玩家說話或行動」後面接一句例外：「例外：{names} 這回合把行動交給 GM，可以替他安排一個小動作，但不替他說話、不替他做重大決定。」名單空時提示一字不變。結果：host 回合派工的 actions 是空的，`action_id` 也不同，名單必定是空的；retry 與執行端重連續跑用的是同一個派工，標記照樣對得上；regenerate 會以新的派工重新落同一批 skipped，標記帶新的 `action_id`；同一派工的鏈裡（旁白 → NPC → 再旁白）都算同一回合。一般單人桌沒有 `action_id`，名單為空。
- 故事串：該玩家的段落標「（交給 GM）」；房主已送出名單、名單頁狀態文字 `statusSkipped` 改「交給 GM」。
- 倒數到期：沿用現況（未送出算觀望、草稿保留），與本鈕無關。

## 3 現有「請 NPC 發言」「讓 X 接話」的處置

**留，但做兩件事：改名，以及不再默默退回別人的行動。** 房主控制 NPC 什麼時候開口，屬於 GM 的正常權力，不需要拿掉。

**改名**（玩家會看到）
- 選單項目：「請{名字}發言」改成「讓 NPC {名字} 說一句」。選單裡的 NPC 前面加一個小標題「NPC」。
- 原本交給 GM 當 NPC 的離座玩家卡，名字後面加「（離座，GM 代演）」，房主一眼就知道那不是在場的人。在場和代管中的玩家卡照現在的規則，不會列進來。
- 「讓{名字}接話」改成「讓 NPC {名字} 接話」，hint 不變。
- 提示文字裡的「不經 GM」容易誤讀，改成「直接請這個 NPC 說一句，GM 不先旁白」。

**不再丟掉已送出的行動**（本案的根因修正，旁白、推進、NPC 說一句、接話四種房主 GM 鈕都適用）

現況：`host.gm` 先 `cancelRound`，已送出的行動退回草稿，再開 host 回合。

*玩家會看到*
- 房主回合進行中：有送出的人，行動格維持「已送出」（唯讀，收回鈕要等房主回合結束）。
- 房主回合結束、新的 `acting` 回合開出來，名單裡還有人沒送出時：有保留行動的人，行動格上方出現「房主讓巴頓先說了一句，你的行動還在，要改可以收回」，送出、收回或回合結束時消失。這行由客戶端判斷（上一回合是 host、自己的格在新回合開出時就是 submitted／skipped），不新增事件。
- 房主：有人已送出時，GM 鈕的提示寫「已送出的 2 個行動會保留，NPC 說完後照樣結算」。不另跳確認框。
- 拿掉原本「故事串多一行系統段『房主請巴頓先開口』」：要重連後也看得到就得進 `storyOf` 並佔段號，成本不值；NPC 那段本身與上一條提示已足夠說明。

*資料存在哪*
- 房間狀態新增一欄 `carry`（`RosterEntry[]`，只放 submitted／skipped 兩種），跟 `returned`、`returning`、`departures` 一樣隨房間狀態在同一筆交易落地。不放在回合物件上，因為 `openRound`、`reopen` 都整份替換 `s.round`。
- host 派工不帶這批行動：host 回合的 `batch` 照舊是空的，`ensureDispatch` 的 `actions` 也就是空的；`players` 照舊取當下的 `activeMembers`。
- 公開性：submitted 的原文送出時就已公開（裁決 9），所以快照的 `round` 與 host 回合的 `round.opened` 都帶 `carry`，給客戶端顯示「已送出」與重連用。

*存進 carry（兩個入口，共用一個 helper：把當前 acting 名單裡 submitted／skipped 的格移進 carry，其餘照 `cancelRound` 處理登場者）*
1. `host.gm`：取代原本的 `cancelRound`。發 `round.cancelled { round, kept: true }`，客戶端看到 `kept` 就不把原文搬回自己的草稿。
2. `round.undo` 收回的是 host 回合、當下是它後面那個 `acting`（`undoResult` 裡 `lastDispatch.host` 有值、`round.phase === "acting"`）：取代原本的 `cancelRound`，取**結果到達當下**的名單。玩家在 host 回合之後收回或改寫過的內容因此都以現況為準；`s.undo` 等待期間 `roundAt` 擋住一切行動指令，名單不會在中途變動。收回一般 play 回合時照現況退回草稿，不在本案範圍。

*從 carry 恢復（單一出口：`openRound(tx, "play")`）*
- `openRound` 開 play 回合時，名單照舊從 `activeMembers` 建，然後在同一筆交易裡逐一比對 carry、清空 carry。下列出口都經過它，不另寫分支：
  - `gen.done`（含房主中止後執行端回的 `aborted`）。
  - `gen.failed` → held → 出額度者 retry／切換 → 回到 generating → `gen.done`。held 期間 carry 原封不動。
  - held → `round.continue`。
  - held 的 host 回合被收回：edit 直接 `openRound("play")`；regenerate 走 `reopen` 開新的 host 回合，carry 不動，等它 `gen.done`。
  - 收回 host 回合後面的 acting（上一段入口 2）：edit 同筆交易就恢復；regenerate 同上。
  - 重開補送 `applySync` 遇到 held：先 `openRound("play")` 恢復；若這次有補送內容，接著的 `cancelRound` 再照作者裁決（2026-11-03）把已送出的退回。兩步都在同一筆交易。
- 冪等：`gen.done` 先比 `lastDoneDispatch`，再過 `live()`；`round.continue` 重送會被 `roundAt(held)` 擋；收回結果靠 `jobId`／`doneJobs`。carry 在第一次恢復時就清空，所以重送不會再套一次。
- 有效性（每一格）：新名單裡有同一個 `memberId` 而且 `cardId` 相同，就恢復成原本的 submitted（帶原文）或 skipped。新名單本身只含入座、未封鎖、未代管的人，所以離座、被踢、被封鎖、改成代管、換了卡的，都自然對不上。
- 失效格：skipped 直接丟掉（沒有內容）。submitted 的原文用既有 `returned` 機制還給原 `memberId`（成員還在、未封鎖才給；`vol.returned` 只送本人）。不寫進草稿，因為 host 回合期間玩家可能已經打了新草稿；`returned` 的客戶端本來就是「輸入框空就直接放回，有草稿就另外顯示可帶回或丟掉」。已有一筆沒處理的 `returned` 時，用換行接在後面，不覆蓋。
- 換座：`member.reassign` 已經把名單上的 `memberId` 改成接手的人，同一處也把 carry 的 `memberId` 改過去，行動跟著卡走，與草稿、`returned` 的處理一致。

*丟掉 carry（不經恢復就離開 host 回合的出口）*
- `cancelRound` 一律先把 carry 交給上面的「失效格」處理再清空：涵蓋 held（`scene_full`）時換幕、`syncScene` 補送換幕。這與現況「換幕時已送出的退回」一致，只是改走 `returned`，不覆蓋玩家剛打的草稿。
- 關房：carry 跟著房間狀態保存，重開走 `applySync`，同上。

*恢復後的結算*
- 照一般 `acting` 規則，不另訂等待規則：新名單裡還有人沒送出就等；如果恢復後全員都是 submitted／skipped（例如唯一還沒送出的人在房主回合期間改成代管或離座），交易尾端的 `settle` 會立刻結算。這時玩家沒有機會依 NPC 的話修改，接受這個代價，因為等待的人已經不在名單上。新回合的倒數照設定重新計時。
- 為什麼不改成「有人送出就不准按」：房主插一句 NPC 是正常的帶團節奏，擋掉會讓這顆鈕在多人桌上幾乎不能用。

## 4 單人版的「請他發言」：不改

單人桌只有一位人類玩家。「請他發言」的意思是「我這次不輸入，讓被點名的角色接話」：沒有別人會被打斷，也沒有行動會被丟掉，玩家就是決定的人。作者說的兩個問題（字面像在催別人、房主替玩家決定）在單人版都不存在。文案「不輸入玩家發言，直接請被點名的角色接話」也已經寫清楚。所以不改，免得兩邊說法分岔。

## 5 案別估計

| 部分 | 核心行數 |
|---|---|
| §1 催促（伺服器指令、驗證、`rate` 冷卻約 15；手機橫條、震動、房主按鈕約 45） | ~60 |
| §2 交給 GM（執行端 Watch 帶理由與新標記約 15，提示詞例外約 10，改名與故事串、名單文字約 10） | ~35 |
| §3 帶著已送出的行動過房主回合（伺服器：carry 欄位、存入 helper、`openRound` 恢復與有效性、失效格走 `returned`、`cancelRound` 丟棄、`undoResult` 分支、換座一行、快照與型別約 60；客戶端：host 回合顯示已送出、`kept` 不搬草稿、提示列約 25；改名與離座標記約 15） | ~100 |
| 合計 | **約 195 行，屬於中案** |

雖然是中案，但 §3 改動回合狀態機，又牽涉「一般玩家正常操作會遇到的資料遺失」（已送出的行動），照規約要先**送方案審**。i18n 三語不計入核心。

驗收集中在：交給 GM 的 play 回合完成 → 房主按推進，host 回合的提示詞不帶例外；host 回合三種結束方式（完成、中止、失敗後繼續）都恢復；失敗後 retry 再完成也恢復；收回／重生 host 回合（held 與後面的 acting 兩種位置）；host 回合中代管、離座、換座、被踢的格；恢復後全員已送出立刻結算；換幕時 carry 走 `returned`。每條比對即時事件與重連快照的結果一致即可，不擴成大型故障測試。
