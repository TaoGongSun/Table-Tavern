# vendor-prefix-floor — 只中到 CLI／供應商自帶底線的輪次，不該報成已省

## 問題

各 CLI／供應商會快取自己的固定開頭，那段與我方送什麼無關，冷啟動也會中。額度分頁只看 `cached_tokens > 0` 就報命中：2026-10-28 實測 codex 0.164.0 自帶段 11,008（舊版 9,984，隨 CLI 版本變），9 通我方 0 命中卻全標 hit，命中條顯示 36–76%（實測佇列第 14 項）。

作者裁決 2026-10-06：只中到 CLI／供應商自帶底線的輪次，頭條不算「已省」，改標「只中到 CLI 自帶部分」。

## 定案（2026-10-28 主線＋Sol＋Grok 兩輪審查收斂）

**底線（`usage/floor.rs`，純函式）**：組內真實回報（`reported()`，排除 unknown／unreported、事件、舊保溫 ping、生圖）的正值裡，出現 ≥3 次、且對上至少兩種不同 `prompt_tokens` 的最小值；0 不當底線；沒有合格值＝未辨識，畫面維持現行。理由：共線穩定成功時成功量通常大於自帶段，取最小合格值不會被成功量搶走；要兩種輸入量才排除「同一段輸入重送、我方內容真的中了」。

兩道護欄（重放正式帳本後加）：沒有自帶段的路，我方共線前綴穩定命中時本來就會在不同輸入量下重複同一值（API muse-spark 12,337×3，底下 15 筆更小的真命中），會被誤認成底線。
- 候選值底下的正值超過一成（至少容許一筆偶發，例：codex 6,912）就不認，整組未辨識。
- API 底線上限 128（一個量化區塊）：API 供應商不加自帶提示詞，固定小值只是計量零頭（ox-alpha 64）。

重放結果：codex 9,984（舊）／11,008（0.164.0）、grok 128、ox-alpha 64 判出；muse-spark、union-alpha（2,028×4，幾乎是我方整段 system）、claude-opus-4-6（11,266，底下 20 筆更小）未辨識。

**分組**：CLI＝（通道、模型、`cli_version`）；API＝（通道、模型、`endpoint`）。缺欄歸「未知」組。全檔分組算完再套到選桌，選哪一桌判定都一樣。

**帳本可選欄**（作者同意加，舊行照讀〔作者裁決 2026-10-28〕）：`cli_version`＝runner 以同一執行環境跑 `--version` 的第一行（與呼叫並行、5 秒上限、依路徑＋mtime 快取、落帳時沒查好就不寫）；`endpoint`＝API 實際打的 `主機:連接埠#路徑雜湊`（沒寫連接埠補協定預設值；路徑去掉 query、fragment、帳密後取 FNV-1a 雜湊前 8 碼，路徑本身不落帳，以防閘道把金鑰放路徑裡）——同一主機不同連接埠或路徑可能代理不同供應商（Sol 驗收）。

**判定**：帳本記 `hit`、算不出理論可中量（無 lane，或有效期望為 0——重開那輪一律 0）、且 0 < 讀到量 ≤ 底線 → `vendor-only`（API 為 `vendor-only-api`）。快取有順序、自帶段在最前，低於底線同樣是我方 0 命中。`partial`／`missed` 與算得出理論量的續聊線不走這條。底線之上不設容差。黃燈 `warn`，只在明細出現。

**省額（B2，作者裁決 2026-10-28）**：已辨識底線的組每輪先扣自帶段 `min(讀到量, 底線)`：省額＝原省額 − 自帶段×(1−讀係數)，已省只算我方內容讀到的部分，消掉「讀到底線算 0、多 1 就全額」的斷崖（codex：讀到 12,000＝我方讀到 992、省下等值 892.8）。只中自帶的輪次走同一公式（codex／grok 寫入不加價，結果正好 0），不另設強制 0；寫快取加價照算、省額可為負。未辨識底線扣 0＝原算法。輸入量整段留在頭條分母；美元照原實付等值反推單價，只換省額分子。原始用量、花費與明細表照列。

**claude 通道不認底線**〔模型判斷·未裁決〕（主線＋Sol＋opus-review 共識 2026-10-28）：目前統計分不出 claude 自帶段與我方固定前綴。app 同參數實測（claude 2.1.311、極短 system）：CLI 自帶整段 2.1k–3.0k，opus-4-7／opus-4-8／sonnet-4-6 讀不到快取，sonnet-5-5 讀 1,206；帳本判出的 10,417／3,223／11,494 是我方 system 穩定命中；帳本佐證：opus-4-7、opus-4-8、sonnet-5-5 各組讀到剛好底線的輪次都只出自同一個 `system_hash`，sonnet-4-6 那 12 輪是沒有 hash 的舊行、全在同一桌。`floors()` 不收 claude 樣本，命中格、命中條、頭條、最近一輪燈號與省額一致不套底線；`floor.rs` 對外語意不變。

**畫面**：範圍內有 `vendor-only` 輪且沒有任何其他讀到快取的輪次 → 頭條改標「只中到 CLI 自帶部分」（全是 API 時「只中到供應商固定開頭」），不顯示「已省 0%」。已辨識底線時命中條三段：我方命中（估）＝讀到量−自帶段、自帶＝每輪 min(讀到量, 底線) 加總、全額；共用原始輸入分母。未辨識時維持兩段。

## 已知限制

- 暫態、會自癒：新版本剛上線、自帶段還沒出現滿 3 次時，成功量可能先被當底線（Sol 反例：11,008×1＋18,176×3 → 底線 18,176，那幾輪被標成只中自帶）。自帶段每次冷啟動都會出現，補滿 3 次後最小合格值自動回到 11,008，讀帳時舊輪一併重判；不做人工校準綁定〔模型判斷·未裁決〕（主線裁決 2026-10-28）。
- CLI 路若沒有自帶段、而我方前綴的重複值底下又沒有足夠更小的命中，護欄擋不住，仍會誤認。
- claude 不認底線後，前案標成只中自帶的 24 輪 claude（opus-4-7 4、opus-4-8 3、sonnet-4-6 12、sonnet-5-5 5）改顯示為命中；其中 sonnet-5-5 那 5 輪底線 1,295 接近實測 CLI 自帶 1,206，大致真是只中自帶，現在算成我方命中，sonnet-5-5 全組 37 輪也不再扣自帶段（全帳本約 4.3 萬）〔模型判斷·未裁決〕。
- 算得出理論可中量、讀到量卻低於底線的續聊輪（前案既有）：格子顯示「中了」，但我方實讀 0、省 0。
- sonnet-5-5 的已省因此下降（重放約 91 萬→74 萬）：那 5 輪是重建時寫入整段快取，原本被強制記 0，現在寫入加價照算成負省額。
- 加欄前的舊行全歸「版本未知」組：正式帳本 codex 舊行底線取到 9,984；若舊行裡混了新版 11,008 的輪次，那輪顯示成我方中了 1,024。不做時間切段。
- CLI 升級後新版本組要累積 3 筆、兩種輸入量才判定，之前維持現行顯示。
