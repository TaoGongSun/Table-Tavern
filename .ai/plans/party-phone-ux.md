# party-phone-ux：多人房間手機介面改版（方案）

依據：`party/src/features/room/*`、`App.css`、說明書手機截圖 room-13/15/17/19（300×650 CSS px）。

## 我看到的問題（玩家會遇到什麼）

1. **上方疊了四層，吃掉 160–180px**：品牌列（Table Tavern＋房號＋一個很寬的語言選單）→ 回合列（回合號、狀態、「GM：預設」、「還在等：…」常常兩三行）→ 分頁列（玩家只有「故事／名單」兩顆）→ 場景列（時間地點在場，常兩行）。玩的時候真正要看的只有「現在輪到誰／剩多久」。
2. **下方也疊三層，約 180px**：一顆滿版沒邊距的「編輯我的角色」（看起來像壞掉的條）＋三行高的輸入框＋獨立一列「跳過／送出」。劇情區只剩不到一半。
3. **開鍵盤後劇情幾乎看不見**：版面高度跟著可見區域縮，但上下的固定層一層都不讓，剩下的空間全被擠掉——玩家打字時看不到 GM 剛剛說了什麼，只能來回收鍵盤。這是回饋「劇情太小」的主因。
4. 語言選單、房號、GM 模型名是一次性或資訊性的東西，卻常駐在最貴的位置。
5. 名單頁對每個玩家都攤開「我要用自己的額度跑 GM：輸入配對碼」，這件事少數人才會做，卻佔掉名單頁一大塊。

## 改法（只動手機版；桌面版嵌入 `.party-embedded` 版面不變）

A. **上方合成一列（約 44px）**：房間內不顯示品牌列；這一列左邊是回合摘要（「第 2 回合 · 輪到大家行動 · 1:20」，放不下省略），右邊是精簡分頁鈕（故事／名單／房主／額度）。點摘要展開細節（GM 模型、還在等誰、倒數說明）。房主可操作的東西（結算、中止、卡住處理、離線者的代管鈕、重開提醒）照常露出，不藏。
   → 劇情多出約 80px，狀態仍一眼看到。
B. **場景列預設一行**（省略號），點一下展開到三行。 → 再省 15–20px，長的「在場」名單點開就看得到。
C. **「編輯我的角色」移到名單頁自己那一列**（「編輯」鈕）；房號與語言選單也移到名單頁底部。加入前的畫面（填暱稱、沒邀請連結）品牌列與語言選單照舊。
D. **輸入格改成聊天式**：輸入框一行起跳、隨內容長高（上限約 5 行），「送出」放在輸入框右邊同一列；「跳過」與房主的 GM 鈕縮成輸入框下的一條細列小鈕。行為（草稿、收回、帶回、提示句）一律不變。 → 下方從約 180px 降到約 100px。
E. **打字時讓位給劇情**：輸入框有焦點時收起場景列、回合列只留一行。鍵盤開著時劇情區約從 0 變成 200px 以上，能邊看 GM 剛說的話邊打。
F. 名單頁的配對碼表單收成一行「用自己的額度跑 GM ▸」，點開才顯示。

G. **（回應作者 1：平時收起、靠近才出現）**觸控沒有 hover，「靠近」對應成兩個手勢：
   - **往回捲讀舊劇情時自動收起**：劇情區離開最底部超過約一屏，上方的合併列與場景列縮成一條 24px 細條（只剩「第 2 回合 · 1:20」），輸入格縮成一顆「寫行動 ▴」小鈕。捲回最底、點細條或點小鈕就全部展開。這是 Safari、Chrome 手機版的網址列做法，玩家已經熟悉。
   - **點一下展開**：A 的回合摘要、B 的場景列平時只顯示一行，點了才展開細節。
   - 例外不收的〔模型判斷·未裁決〕：卡住時的處理鈕、房主可操作的代管鈕、倒數最後 30 秒——這些是要你現在動手的，藏起來會誤事。
   - 不做「點劇情區切全螢幕」：點劇情和點按鈕很容易誤觸，捲動收起已涵蓋同樣需求。
H. **（回應作者 2：玩家自己調字級）**做。名單頁底部的「顯示」區（跟搬過去的語言選單放一起）加四段字級「小／中／大／特大」（劇情 15／17／19／22px，預設中＝17px，比現在的 16px 略大），只改劇情段落與輸入框，按鈕與狀態列不跟著放大，免得字大了空間又被吃回去。存在這支手機的瀏覽器裡，下次進房還是同一級；只影響自己，不影響其他玩家。桌面版嵌入照舊用桌面 app 自己的字級設定，不加這個選項。
   放名單頁而不是故事頁的理由一句：一次性設定不該常駐在劇情旁邊佔位（同 C）。

合計：鍵盤沒開時劇情區從約 310px（48%）→ 約 480px（74%）；鍵盤開著從幾乎 0 → 約 200px。

補充說明：
- A 的 44px 是**入座玩家**的數字。房主（與出額度者）有動作鈕時多一列動作列；「還在等」裡離線者的代管鈕只對房主出現，那時「還在等」那行照常露出、不收進展開細節（能操作的東西不藏）。
- 位置變動、可能要作者拍板的：**C（編輯角色、房號、語言選單搬到名單頁）**、**D（跳過改成輸入框下的小鈕）**、**G（捲動時自動收起）**、**H 的預設字級從 16 改 17px**。其餘是純版面。

## 不改的〔模型判斷·未裁決〕
- 字級 16px、配色、劇情段落樣式不動（字不小，問題是空間）。
- 桌面版嵌入版面不動：桌面版的 `src/styles/room.css` 只覆寫 `.party-embedded` 的一部分，`App.css` 的 `.app .x` 兩邊都吃得到。做法是手機外殼在 `.app` 加 `party-phone` class，新 CSS 全掛在它底下；結構差異（品牌列、編輯鈕位置）走現有的 `c.pairForm !== false` 分支。

## 案別估計
中案：核心約 220–300 行（G、H 約多 70 行）（多為 CSS＋RoomScreen/RoundBar/ActionBox/scene-status 版面調整），不碰信任邊界與資料流。`room.test.tsx` 有約 34 處用到要搬的 testid（`card-edit`、`tab-*`、`scene-status`、`round-bar`、`action-text`），testid 盡量保留，主要改「編輯角色」的點擊路徑，估測試改動 <100 行。做完送一位審查員驗收。

## 實測
本機 `party` 的 `dev:server`（wrangler 本機）＋`dev`（vite），房主由測試通道的桌面 app 開房連本機伺服器，手機端用內建瀏覽器 375×812 進邀請連結；截圖：一般遊玩、鍵盤開（以縮小視窗高度模擬）、名單頁、房主沒入座、大廳選角。若桌面 app 連本機伺服器有阻礙，改用 `fake-server` 寫一個只在 scratchpad 的預覽入口。

- 實作核心約 +560／−108 行（含 CSS 約 175 行），超出立案估計（220–300）；主因是 CSS 與 ActionBox 版面重排。
- 實測用本機預覽：真的房間核心跑在瀏覽器、腳本扮演執行端與其他玩家（`fake-server` 的 Hub），沒走桌面測試通道；桌面嵌入版面沒動到介面行為，沒跑測試通道。
